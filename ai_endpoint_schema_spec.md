# AI_ENDPOINT_SCHEMA_SPEC.md

## Purpose

This document defines the canonical backend endpoint contracts and schema expectations for Redline Simulator Engine (RSE).

These endpoints exist to provide **dynamic augmentation** to the simulation while preserving engine authority. They are designed for use by both the web client and the desktop fallback build through the same backend API.

This specification defines **target contracts**. Implementations must conform to these schemas and principles even if internal prompt strategies change.

---

## 1. Canonical AI Boundary

AI endpoints may provide:
- dynamic news copy
- inbox and executive messaging
- contract clause variation
- coaching nudges
- post-turn analysis
- scenario flavor augmentation
- educational explanation

AI endpoints must never directly:
- mutate simulation truth
- alter accounting truth
- determine authoritative scores
- bypass the decision resolver
- replace deterministic event resolution

All endpoint outputs are advisory or presentational unless explicitly routed back into the engine through approved deterministic rules.

---

## 2. General API Conventions

### Base Path
All production routes should be versioned.

Example:
- `/v1/gen/news`
- `/v1/gen/inbox`
- `/v1/coach/nudge`
- `/v1/score/analysis`

### Content Type
Requests and responses use JSON.

### Authentication
Production requests should use backend-controlled auth mechanisms appropriate to the hosting model.

### Validation
Every request must be validated server-side before provider calls.
Every response must be validated server-side before being returned to the client.

### Traceability
Each response should include:
- request identifier
- schema version
- generation mode
- fallback flag where relevant

---

## 3. Shared Request Envelope

All AI endpoints should accept a standard outer envelope with endpoint-specific payload nested inside.

```json
{
  "request_id": "uuid-string",
  "schema_version": "1.0",
  "client": {
    "platform": "web",
    "build_version": "0.1.0",
    "environment": "staging"
  },
  "scenario": {
    "scenario_id": "flightpath_001",
    "scenario_version": "1.0.0",
    "domain_module": "flightpath"
  },
  "run_context": {
    "run_id": "uuid-string",
    "turn_index": 4,
    "week": 4,
    "month": 1,
    "quarter": 1,
    "year": 1,
    "seed": 12345
  },
  "payload": {}
}
```

### Shared Field Rules

#### request_id
Unique request identifier generated by the caller.

#### schema_version
Version of the endpoint contract expected by the caller.

#### client
Client metadata for diagnostics and rollout control.

#### scenario
Scenario identity and version.

#### run_context
Core simulation context for the current run.

#### payload
Endpoint-specific request body.

---

## 4. Shared Response Envelope

All endpoints should return a standard outer response envelope.

```json
{
  "request_id": "uuid-string",
  "schema_version": "1.0",
  "status": "ok",
  "fallback_used": false,
  "provider": {
    "name": "openai",
    "model": "gpt-5.4"
  },
  "result": {},
  "warnings": [],
  "errors": []
}
```

### Response Rules
- `status` should be `ok`, `fallback`, or `error`
- `fallback_used` must be explicit
- `result` must conform to endpoint-specific schema
- `warnings` may contain non-fatal issues
- `errors` should contain safe, non-sensitive descriptions

---

## 5. Context Compression Rules

AI requests must not dump the entire game state into prompts like a panicked intern emptying a filing cabinet onto the floor.

Each endpoint should receive only:
- the minimum scenario context needed
- relevant KPIs
- relevant recent events
- player-facing framing
- specific task constraints

All payload builders should be explicit and deterministic.

## 6. Endpoint: /v1/gen/news

## Purpose
Generate dynamic news items or media-style blurbs reflecting recent deterministic game outcomes.

## Request Payload Schema

```json
{
  "news_type": "weekly_wrap",
  "tone": "professional",
  "audience": "internal_exec",
  "recent_events": [
    {
      "event_id": "fuel_spike_01",
      "event_type": "cost_shock",
      "headline_hint": "Fuel prices rose sharply",
      "severity": "high"
    }
  ],
  "kpis": {
    "revenue": 1250000,
    "expense": 980000,
    "cash": 540000,
    "margin_pct": 21.6,
    "audit_score": 78
  },
  "constraints": {
    "max_items": 2,
    "max_words_per_item": 90
  }
}
```

## Response Result Schema

```json
{
  "items": [
    {
      "id": "news_001",
      "headline": "Fuel Costs Pressure Monthly Margin",
      "body": "A sharp increase in fuel expense narrowed margin this week, forcing leadership to revisit route economics and operating discipline.",
      "tone": "professional",
      "tags": ["costs", "margin", "operations"]
    }
  ]
}
```

## Rules
- News must reflect deterministic inputs only
- No invented financial facts outside supplied context
- Tone and audience must be respected
- Response must be render-safe and concise

## 7. Endpoint: /v1/gen/inbox

## Purpose
Generate inbox messages, executive emails, alerts, or internal memos tied to game state.

## Request Payload Schema

```json
{
  "message_type": "executive_email",
  "sender_role": "cfo",
  "recipient_role": "player",
  "objective": "highlight liquidity concern",
  "facts": {
    "cash": 240000,
    "cash_change_pct": -18.5,
    "month": 2,
    "audit_score": 62
  },
  "constraints": {
    "max_words": 140,
    "urgency": "medium"
  }
}
```

## Response Result Schema

```json
{
  "message": {
    "subject": "Liquidity Needs Immediate Attention",
    "from_label": "CFO Office",
    "body": "Cash has tightened faster than expected this month. Before approving new commitments, review expense timing and near-term cash protection options.",
    "priority": "medium",
    "tags": ["cash", "liquidity", "finance"]
  }
}
```

## Rules
- Must remain grounded in supplied facts
- Must not issue deterministic commands pretending to mutate state
- Should be concise and role-appropriate

## 8. Endpoint: /v1/gen/contract_clause

## Purpose
Generate optional dynamic prose for contract sections while preserving machine-readable contract terms controlled by the engine.

## Request Payload Schema

```json
{
  "contract_type": "supplier_framework",
  "clause_type": "service_level",
  "counterparty": {
    "name": "Northstar Fuel Services",
    "region": "EMEA"
  },
  "structured_terms": {
    "max_lead_days": 10,
    "base_price_usd": 4.25,
    "penalty_pct": 8,
    "termination_notice_days": 30
  },
  "style": {
    "voice": "formal_commercial",
    "jurisdiction": "generic_demo"
  }
}
```

## Response Result Schema

```json
{
  "clause": {
    "title": "Service Level Commitment",
    "body": "Supplier shall maintain delivery performance sufficient to meet the agreed service windows set forth in this framework, subject to the lead-time and remedy provisions defined herein."
  }
}
```

## Rules
- Output is presentational clause language only
- Structured terms remain authoritative
- Generated prose must not contradict structured terms
- Backend should validate term consistency before returning

```json

  },
  "situation": {

    "expense_growth_pct": 14.2,
    "audit_score": 55
  },
  "constraints": {
    "max_words": 80,
    "tone": "supportive"
  }
}
```

## Response Result Schema

```json
{
  "nudge": {
    "title": "Look at Margin Drivers",
    "body": "Revenue alone is not the whole story here. Compare the benefit of your recent pricing move against the cost pressure now showing up underneath it.",
```

## Rules
- Must guide, not solve
- Must not reveal hidden future events
- Must remain educational rather than manipulative
- Should point toward relevant business concepts

## 10. Endpoint: /v1/score/analysis

## Purpose
Generate explanatory analysis of player performance after deterministic scoring has already been computed by the engine.

## Request Payload Schema

```json
{
  "evaluation_window": "month_close",
  "scores": {
    "points_awarded": 12,
    "audit_score": 73,
    "mission_result": "pass"
  },
  "decision_summary": [
    "reduced discretionary spend",
    "accepted higher-cost fuel contract",
    "protected cash"
  ],
  "financial_summary": {
    "cash_change": 45000,
    "margin_pct": 16.1,
    "revenue_change_pct": 2.3,
    "expense_change_pct": 7.2
  },
  "constraints": {
    "max_words": 180,
    "tone": "executive_review"
  }
}
```

## Response Result Schema

```json
{
  "analysis": {
    "headline": "Disciplined but Costly Month",
    "summary": "You protected liquidity and passed the mission gate, but the quality of the win was weakened by cost inflation that outpaced revenue improvement.",
    "strengths": [
      "Cash protection improved resilience",
      "Mission objectives were met"
    ],
    "risks": [
      "Expense growth outpaced revenue growth",
      "Cost structure remains exposed"
    ],
    "concept_tags": ["liquidity", "margin", "operating_discipline"]
  }
}
```

## Rules
- Analysis must interpret deterministic scores, not invent them
- The engine remains authoritative for points and pass/fail outcomes
- The endpoint explains consequences; it does not decide them

## 11. Endpoint: /v1/scenario/augment

## Purpose
Generate tightly constrained scenario flavor content such as optional narrative framing, short event descriptions, or atmosphere text.

## Request Payload Schema

```json
{
  "augmentation_type": "event_flavor",
  "event_stub": {
    "event_type": "regulatory_notice",
    "severity": "medium",
    "business_area": "compliance"
  },
  "tone": "serious",
  "constraints": {
    "max_words": 70
  }
}
```

## Response Result Schema

```json
{
  "augmentation": {
    "title": "Regulator Requests Clarification",
    "body": "A formal notice has been issued requesting clarification on recent compliance disclosures, increasing scrutiny ahead of the next review cycle."
  }
}
```

## Rules
- Flavor only
- Must not create new authoritative mechanics without engine approval
- Best used for atmosphere, not hidden state

## 12. Canonical Error and Fallback Schema

When an endpoint cannot return model-generated content, it must return a safe fallback envelope.

```json
{
  "request_id": "uuid-string",
  "schema_version": "1.0",
  "status": "fallback",
  "fallback_used": true,
  "provider": {
    "name": "openai",
    "model": "gpt-5.4"
  },
  "result": {
    "fallback_message": "Dynamic commentary is temporarily unavailable.",
    "fallback_content": {}
  },
  "warnings": [
    "provider_timeout"
  ],
  "errors": []
}
```

## Rules
- Fallback must be renderable
- Fallback must not break client parsing
- Client UX must remain coherent

## 13. Canonical Backend Validation Rules

Every endpoint implementation must validate:

### Request Validation
- required fields present
- correct scalar and object types
- field length limits
- allowed enum values
- scenario compatibility
- payload size limits

### Response Validation
- provider output parses cleanly
- required result fields exist
- lengths remain within constraints
- no contradiction of authoritative input facts
- no prohibited content category
- no schema drift

---

## 14. Canonical Prompting Rules

Prompt builders should follow these rules:

1. Use only minimal relevant context
2. Provide explicit role and task definition
3. State non-negotiable facts from the engine
4. State prohibited behavior
5. State length and tone constraints
6. Request structured output only
7. Never ask the model to decide authoritative game state

---

## 15. Canonical Cost and Latency Rules

### Cost Controls
Each endpoint should define:
- target model tier
- max output length
- fallback behavior
- cache eligibility

### Latency Controls
Each endpoint should define:
- timeout threshold
- retry policy
- stale-cache policy where safe

### Priority Guidance
Recommended early priorities:
- `/v1/gen/news`
- `/v1/gen/inbox`
- `/v1/coach/nudge`

These provide high visible value with relatively low structural risk.

---

## 16. Canonical Security Rules

- No raw provider secrets exposed to clients
- No prompt injection trust in client text
- No provider output returned unvalidated
- No endpoint should accept arbitrary unrestricted simulation dumps
- Sensitive logs must be minimized

---

## 17. Final Endpoint Statement

Redline’s AI endpoint layer exists to provide **controlled dynamism**.

The engine remains deterministic and authoritative.
The backend converts narrow, structured simulation context into safe dynamic augmentation.
The client renders the result.
No endpoint may become the accidental ruler of the simulation.
